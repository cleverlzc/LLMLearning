# Mooncake 四个工程技巧：让数据高速公路"会思考"

> **系列**: Mooncake 技术博客系列 | **类型**: 工程模式篇

智能算法可将基础数据高速公路转变为智能、自我优化的网络 -- 一条会思考的数据高速公路。Mooncake运用一系列技巧，将基础数据高速公路转变为智能、自优化的网络。

移动数据是一回事，快速移动数据——这才是真正工程技术的体现。Mooncake 运用四个工程巧妙技巧，将基础数据高速公路转变为智能、自优化的网络：多通道切片传输、SIEVE 端点池化、拓扑感知路由、Count-Min Sketch 淘汰。

每个技巧都能解决数据高速公路中的特定性能瓶颈。你可以根据工作负载和硬件进行灵活搭配，或者火力全开。

---

### 引言

想象一个智能交通管理系统。它不会让每辆车都走同一条高速公路，而是将交通分流到多条车道上，监控哪些车道行驶速度较快，当某条车道被堵塞时重新分配车道，并且重复利用收费站，而不是每次出行都新建收费站。

高性能分布式系统不仅使用快速的硬件，还使用智能算法从硬件中提取最大吞吐量。多轨切片（Multi-rail slicing）、连接池（connection pooling）和近似数据结构（approximate data structures）都是使硬件发挥更大作用的软件智能。

Mooncake 面对的是一个极端场景：8 卡 GPU 服务器每秒产生数 GB 的 KV Cache，需要在节点之间高速搬运。硬件已经很快了（100 Gbps RDMA），但如果没有软件智能，硬件的潜力远未被榨干——单网卡带宽饱和、连接建立开销、跨 NUMA 访问惩罚、精确追踪的内存爆炸，每个瓶颈都能把理论带宽砍掉一半。

以下是 Mooncake 用来解决这些瓶颈的四个工程技巧。

### 技巧一：多通道切片传输——给高速公路加车道

将大容量数据传输分散到多个网卡上，就像为高速公路增加车道一样——车道越多，吞吐量越大。

适用场景：在具有多个网卡的机器之间进行大容量传输（64 MB以上）

解决瓶颈：单网卡带宽饱和问题。

一些关键术语：
- 网络接口卡（网卡，NIC）：连接计算机与网络的硬件，就像通往数据高速公路的入口匝道。
- 多通道（Multi-rail）：使用多张网卡并行传输数据，就像在高速公路上增加车道，以便更多车辆可以同时行驶。
- 吞吐量：单位时间内处理的数据量或工作量——例如高速公路每小时能承载多少辆汽车。
- 切片（Slice）：大传输中的一部分（chunk），就像将一个大货物拆分成可以走不同路线的较小包裹。

具体案例：
一个64MB的大数据块传输到达了，传输引擎将其分割为16个切片（每个切片4M，足够小方便传输），8个切片通过NIC1发送，8片通过NIC2发送，带宽翻倍，时间减半（double the bandwidth, half the time），接收端收集所有16个切片，并将它们重新组装成原始数据——传输完成！

#### 瓶颈

单张网卡的带宽有上限。一张 100 Gbps 的 Mellanox ConnectX-6 网卡，实际吞吐约 12.5 GB/s。一个 64MB 的 KV Cache 传输需要约 5ms——看起来很快，但当几十个 Decode 实例同时拉取 Prefill 结果时，单网卡就成了瓶颈。

#### 解法

**将大传输切成小切片，分散到多张网卡上并行传输。**

```
64MB 数据传输
  │
  ├─ 切成 16 个切片（每个 4MB）
  │
  ├─ 8 个切片 → NIC1（mlx5_0）──►  远端 NIC1
  │
  └─ 8 个切片 → NIC2（mlx5_1）──►  远端 NIC2
                    │
                    └─ 带宽翻倍，时间减半
```

Mooncake 的实现中，`RdmaTransport::submitTransferTask()` 将每个传输请求按 `slice_size`（默认 64KB）切成多个切片，每个切片独立选择一张网卡：

```
应用调用 submitTransfer(batch, [request])
    │
    ▼
RdmaTransport::submitTransferTask()
    │
    │  request.length = 64MB
    │  slice_size = 64KB
    │  → 切成约 1024 个切片
    │
    ├─ 切片 0: selectDevice() → NIC0 (NUMA 0)
    ├─ 切片 1: selectDevice() → NIC1 (NUMA 1)
    ├─ 切片 2: selectDevice() → NIC0
    ├─ 切片 3: selectDevice() → NIC1
    │   ...
    └─ 切片 1023: selectDevice() → NIC0
```

每个切片通过 `selectDevice()` 独立选择网卡，切片之间天然实现了多通道并行。接收端收集所有切片，通过原子计数器跟踪完成状态——当 `success_slice_count + failed_slice_count == slice_count` 时，整个传输完成。

#### 工程细节：尾部合并

如果最后一个切片只有几 KB，单独发一次 RDMA 写入效率很低。Mooncake 的解法：当剩余数据 ≤ `slice_size + fragment_size` 时，把尾部合并到最后一个切片，避免产生微小的尾部切片。

#### 通用模式

| 系统 | 多通道实现 | 效果 |
|------|-----------|------|
| Mooncake | 多网卡切片传输 | 双网卡带宽翻倍 |
| CDN | Anycast 多路径 | 流量就近分发 |
| MPTCP | 多子流并行 | 带宽聚合 |
| RAID 0 | 多磁盘条带化 | IO 带宽翻倍 |

**本质相同**：把一个大任务切成小份，分散到多条通道并行执行，最后汇总结果。

### 技巧二：SIEVE 端点池化——收费站不拆不建，循环使用

重用 RDMA 连接，而不是每次传输都重新建立连接——就像保持一条车道畅通，而不是关闭再重新打开它。

使用场景：同一机器对之间的高频传输

解决的瓶颈：RDMA 连接建立的开销问题。

一些关键术语：
- SIEVE：一种缓存算法，它决定保留哪些项以及淘汰哪些项，就像游戏俱乐部里的保安一样，追踪最近活跃的用户并移除不活跃的用户。
- 端点（Endpoint）：RDMA网络连接的一端，指软件链接——就像数据通过的收费站。每次都重新创建端点成本较高，因此通过池化和复用可以节省时间。

#### 瓶颈

RDMA 连接的建立成本极高。一次连接需要：

| 步骤 | 操作 | 耗时 |
|------|------|------|
| 1 | 创建 QP（`ibv_create_qp`）× 2 | 数百微秒 |
| 2 | TCP RPC 握手交换 QP 信息 | 毫秒级 |
| 3 | QP 状态机 × 8 次内核转换（RESET→INIT→RTR→RTS × 2 QP） | 数百微秒 |
| 4 | 对端同样执行步骤 3 | 数百微秒 |
| **总计** | | **1~10 ms** |

1~10 ms 建一次连接，在 LLM 推理中是不可接受的——一个 Decode 步骤本身可能只需要几毫秒。如果每次传输都新建连接，连接开销就比数据传输还大。

#### 解法

**池化 RDMA 端点，用 SIEVE 算法决定保留哪些、淘汰哪些。**

```
RdmaContext（每张网卡一个）
  │
  └─ EndpointStore（端点池）
       │
       ├─ getEndpoint("10.0.0.2:mlx5_0")
       │    └─ 命中 → 标记 visited=true → 返回已有端点（< 1μs）
       │
       └─ getEndpoint("10.0.0.3:mlx5_1")
            └─ 未命中 → 创建新端点 → 池满则淘汰 → SIEVE 算法选淘汰对象
```

SIEVE 是一种来自 NSDI '24 的缓存淘汰算法，核心思想极其简洁：

1. **每个端点有一个 visited 位**：每次被查找时标记为 true
2. **淘汰时从尾部扫描**：遇到 visited=true 的清零放行，遇到 visited=false 的淘汰
3. **新端点插入头部**，visited 初始为 true

```
FIFO 列表:  [E_new✓] ... [E_mid] ... [E_old] ← hand 从这里开始扫
                                    ↑
                              hand 扫描方向 ←

扫描规则:
  visited=true  → 清零，放行（"你最近被用过，再给一次机会"）
  visited=false → 淘汰（"你被清零后还没人用你，请让位"）
```

SIEVE 的巧妙之处在于**快速降级（quick demotion）**：第一次扫描就清零 visited 位，而不是像 Clock 算法那样给第二次机会。这意味着一个端点必须在两次扫描之间被再次访问才能存活——自然过滤掉"一次性"连接，保留频繁使用的连接。

#### 对比

| 策略 | 查找开销 | 淘汰精度 | 适用场景 |
|------|---------|---------|---------|
| FIFO | O(1) | 差——不分冷热 | 简单场景 |
| LRU | O(1) 但常数大 | 好——精确追踪 | 通用场景 |
| **SIEVE** | **O(1) 且常数极小** | **接近 LRU** | **高频查找场景** |

SIEVE 的查找路径只需一次哈希查找 + 一次 `atomic_bool` 存储——比 LRU 少了链表操作和写屏障。在 RDMA 端点池这种"查找远多于淘汰"的场景下，SIEVE 的优势尤为明显。

#### 安全淘汰：两阶段销毁

淘汰一个端点不能直接销毁——可能还有在途的 RDMA 写入。Mooncake 用两阶段销毁保证安全：

1. **beginDestroy()**：将 QP 状态改为 ERR，硬件自动刷新在途 WR 到完成队列
2. **finishDestroy()**：等待所有在途 WR 完成（wr_depth 降为 0），然后调用 `ibv_destroy_qp()`

被淘汰的端点先进入 `waiting_list_，定期由 monitor 线程清理。这防止了 use-after-free：工作者线程可能仍在向 QP 提交 WR，而淘汰已经发生。

#### 通用模式

| 系统 | 连接池化 | 淘汰策略 |
|------|---------|---------|
| Mooncake | RDMA 端点池 | SIEVE |
| HTTP 服务器 | Keep-Alive 长连接 | LRU / 超时 |
| 数据库连接池 | JDBC 连接池 | 空闲超时 |
| Redis | 客户端连接复用 | maxclients + LRU |

**本质相同**：连接创建昂贵，复用廉价。用池化避免重复创建，用淘汰策略在池满时腾出空间。

### 技巧三：拓扑感知路由——GPS 选最快车道

根据NUMA和PCIe拓扑结构，为每个内存位置选择最快的网卡——就像GPS选择交通最少的路线一样。

适用场景：具有非统一内存访问的多NUMA、多网卡服务器

解决的瓶颈：跨NUMA内存访问的性能损失问题。

一些关键术语：
- 拓扑结构：指服务器内部CPU、内存和网卡的物理连接方式——就像一张地图，显示哪些入口道路连接到哪些高速公路。
- 非统一内存访问（NUMA）：一种服务器架构，其中某些内存对特定CPU来说比其他内存更近（更快），就像住在某家杂货店附近但离另一家很远一样。
- 外围组件互连快速通道（Peripheral Component Interconnect Express）：这是一种高速总线，用于将网卡、GPU和SSD连接到CPU，就像城市街道将各个街区连接到高速公路一样。

#### 瓶颈

多 NUMA、多网卡服务器内部，不是所有路径都一样快。CPU 访问本 NUMA 节点的内存只需 ~80ns，访问远端 NUMA 节点需要 ~150ns——几乎翻倍。如果网卡在 NUMA 0，数据在 NUMA 1 的内存中，DMA 传输必须跨越 QPI/UPI 互连，带宽和延迟都会受损。

```
┌─────────────────────────────────────────────┐
│                  服务器内部                    │
│                                             │
│   NUMA 0                NUMA 1              │
│  ┌──────────┐          ┌──────────┐         │
│  │  CPU     │  QPI/UPI │  CPU     │         │
│  │  内存    │◄────────►│  内存    │         │
│  │  NIC0    │  跨NUMA  │  NIC1    │         │
│  └──────────┘  惩罚!   └──────────┘         │
│                                             │
│  NIC0 读 NUMA 0 内存 → 快（本地 DMA）         │
│  NIC0 读 NUMA 1 内存 → 慢（跨 NUMA DMA）      │
└─────────────────────────────────────────────┘
```

实测数据（Mooncake 集群拓扑测试）：

| 路径 | NUMA 关系 | 带宽 | 延迟 |
|------|----------|------|------|
| NIC1 → NIC4（同 NUMA） | 1→1 | 21.9 GB/s | 5.67 μs |
| NIC1 → NIC6（跨 NUMA） | 1→0 | 18.9 GB/s | 8.30 μs |
| NIC5 → NIC8（同 NUMA） | 0→0 | 21.9 GB/s | 5.61 μs |

跨 NUMA 访问的延迟增加了约 47%，带宽下降了约 14%。在高速网络中，这是不可忽视的损失。

#### 解法

**根据内存的 NUMA 位置，选择最近的网卡做 DMA——就像 GPS 选择交通最少的路线。**

Mooncake 在启动时自动发现服务器内部的拓扑结构，为每个内存位置构建一张"网卡偏好表"：

```
TopologyMatrix:
  "cpu:0" → preferred_hca: [mlx5_0]  avail_hca: [mlx5_1]
  "cpu:1" → preferred_hca: [mlx5_1]  avail_hca: [mlx5_0]
  "cuda:0" → preferred_hca: [mlx5_0]  avail_hca: [mlx5_1]
  "cuda:1" → preferred_hca: [mlx5_1]  avail_hca: [mlx5_0]
```

- **preferred_hca**：同 NUMA 节点的网卡——DMA 不跨 NUMA，最快
- **avail_hca**：跨 NUMA 节点的网卡——可用但较慢，作为备选

传输时，`selectDevice()` 根据数据的内存位置查表，优先选 preferred 网卡：

```
切片源地址在 NUMA 0 的内存中
  │
  ├─ 查 TopologyMatrix["cpu:0"]
  │
  └─ preferred_hca = [mlx5_0] → 选 NIC0
     （DMA 不跨 NUMA，延迟最低）
```

#### 拓扑发现

Mooncake 通过读取 Linux sysfs 自动发现拓扑，无需手动配置：

| 发现对象 | 方法 | 信息来源 |
|---------|------|---------|
| 网卡列表 | `ibv_get_device_list()` | InfiniBand 驱动 |
| 网卡 NUMA | 读 `/sys/class/infiniband/mlx5_X/device/numa_node` | sysfs |
| CPU NUMA | 枚举 `/sys/devices/system/node/nodeX` | sysfs |
| GPU PCI 地址 | `cudaDeviceGetPCIBusId()` | CUDA API |
| GPU-NIC 距离 | 解析 PCI 路径，计算公共祖先深度 | sysfs |

对于 GPU，拓扑发现更精细——不仅看 NUMA 节点，还计算 PCI 距离。两个设备在 PCI 拓扑树中的公共祖先越近，距离越短，数据传输越快。

#### 重试与故障切换

如果 preferred 网卡故障或过载，系统自动切换到 avail 网卡：

```
retry_count=0: 从 preferred_hca 随机选 → 正常情况
retry_count=1: preferred_hca[0] → 第一次重试
retry_count=2: preferred_hca[1] → 第二次重试
retry_count=N: avail_hca[0] → 降级到跨 NUMA 网卡
```

这就像 GPS 导航：首选路线堵车了，自动切换到备选路线——虽然慢一点，但总能到达。

#### 通用模式

| 系统 | 拓扑感知 | 效果 |
|------|---------|------|
| Mooncake | NUMA/PCIe 感知网卡选择 | 避免跨 NUMA DMA 惩罚 |
| NUMA-aware 分配器 | 内存分配在同 NUMA 节点 | 避免跨 NUMA 内存访问 |
| K8s 拓扑调度 | Pod 调度到 GPU 所在节点 | 避免跨节点 GPU 访问 |
| CSP 亲和性调度 | 任务调度到数据所在节点 | 数据本地性，减少网络传输 |

**本质相同**：数据在哪，计算/传输就放在离数据最近的地方。距离越近，延迟越低，带宽越高。

### 技巧四：Count-Min Sketch 淘汰——用抽样代替普查

一种概率数据结构，它使用恒定内存来估计某事件发生的频率。就像通过抽样几排来估算人群规模，而不是逐一清点每个人的人头数。

适用场景：大型键值缓存池中，精确跟踪成本过高 

解决瓶颈：精确访问跟踪带来的内存开销问题

一些关键术语：
- 概率性方法（Probabilistic）：一种以高概率给出近似正确答案的方法，其内存使用量少于精确方法——例如通过民意调查估算选举结果，而不是统计每一票。
- 驱逐（Eviction）：从缓存中移除旧数据以腾出空间存储新数据的过程——就像清理旧库存以备新商品上架一样。

#### 瓶颈

当存储空间不足时，系统必须决定将哪些 KV Cache 淘汰、哪些提升。最精确的做法是给每个对象维护一个访问计数器，但百万级对象的精确计数需要数百 MB 内存——计数器本身就成了负担。

#### 解法

**用 Count-Min Sketch 在固定 16KB 内存中估算访问频率，用"宁可多留、绝不误杀"的近似判断代替精确计数。**

```
创建一个 4 行 × 4096 列的计数器网格
  │
  │  每个计数器 1 字节（0-255）
  │  总内存 = 4 × 4096 = 16KB
  │
  ├─ 写入: 对 key 做 4 次哈希 → 在 4 行各递增 1 个计数器
  │
  ├─ 查询: 取 4 个计数器的最小值作为频率估计
  │         最小值最接近真实值（其他可能因哈希冲突被高估）
  │
  └─ 衰减: 累计递增达 16,384 次后，全体计数器减半
            旧热度指数消退，新热度持续积累
```

Count-Min Sketch 的数学保证极其重要：**估计值 ≥ 真实值，永远不会低估**。对于淘汰决策来说，这意味着我们可能会稍微多保留一些热门项——这是安全的错误，而非危险的错误。

#### Mooncake 中的两个应用

| 场景 | 角色 | 阈值 | 效果 |
|------|------|------|------|
| Client 端本地热缓存准入 | "二刷门卫" | ≥ 2 才准入 | 过滤一次性冷数据 |
| Master 端 SSD→DRAM 提升 | "频率闸门" | ≥ 2 才提升 | 只提升真正热门的对象 |

默认阈值 = 2，意味着第一次访问不触发任何动作，第二次才准入缓存或提升。这就是"二刷准入"——只给回头客办会员卡。

#### 通用模式

| 系统 | 近似数据结构 | 用途 | 内存节省 |
|------|------------|------|---------|
| Mooncake | Count-Min Sketch | 频率估算 + 淘汰决策 | 16KB vs 数百 MB |
| 数据库 | Bloom Filter | 成员检测 | 固定大小 vs 全量索引 |
| CDN | HyperLogLog | UV 计数 | KB 级 vs 全量日志 |
| 搜索引擎 | MinHash | 文档相似度 | 固定签名 vs 全文比对 |

**本质相同**：用概率数据结构在固定空间内给出"足够好"的近似答案，用微小的精度损失换取数量级的内存节省。

### 四个技巧的协同

这四个技巧不是孤立的——它们在数据传输的每个环节协同工作：

```
应用发起 64MB 传输请求
  │
  │  技巧一：多通道切片
  │  切成 1024 个 64KB 切片
  │
  ├─ 切片 0 ──┐
  ├─ 切片 1 ──┤
  ├─ 切片 2 ──┤  技巧三：拓扑感知路由
  ├─ 切片 3 ──┤  每个切片根据内存 NUMA 位置选最近网卡
  │   ...     │
  ├─ 切片 1022─┤
  └─ 切片 1023─┘
       │
       │  技巧二：SIEVE 端点池化
       │  复用已有 RDMA 连接，不新建
       │
       ▼
  远端接收完成
       │
       │  技巧四：Count-Min Sketch
       │  估算访问频率，决定是否缓存/提升
       │
       ▼
  后续请求命中缓存，无需远程传输
```

| 环节 | 技巧 | 解决的瓶颈 |
|------|------|-----------|
| 传输前 | 拓扑感知路由 | 跨 NUMA DMA 惩罚 |
| 传输中 | 多通道切片 | 单网卡带宽饱和 |
| 传输中 | SIEVE 端点池化 | 连接建立开销 |
| 传输后 | Count-Min Sketch | 精确追踪的内存爆炸 |

四个技巧各管一个瓶颈，互不干扰，可以独立启用，也可以火力全开。

---

### 这些模式不是 Mooncake 独有的

这些模式并非 Mooncake 所独有。连接池化出现在每个网络服务器中（长连接），多路径路由出现在每个CDN中（任播），近似数据结构也出现在每个数据库中（布隆过滤器）。它们在工程世界中反复出现：

| Mooncake 技巧 | 通用模式 | 其他实例 |
|--------------|---------|---------|
| 多通道切片 | 多路径并行 | CDN Anycast、MPTCP、RAID 0 |
| SIEVE 端点池化 | 连接池化 | HTTP Keep-Alive、JDBC 连接池 |
| 拓扑感知路由 | 数据本地性 | NUMA-aware 分配、K8s 拓扑调度 |
| Count-Min Sketch | 概率数据结构 | Bloom Filter、HyperLogLog |

当你深入学习一个系统时，你学到的模式可以应用于任何地方。

- 长连接（HTTP Keep-Alive） 复用现有的TCP连接来处理多个请求，而不是每次都创建新的连接，与 SIEVE 复用 RDMA 连接是同一个模式——连接创建昂贵，复用廉价。
- CDN 的 Anycast（任播） 一种网络路由技术，其中同一个IP地址从多个位置发布，流量被发送到最近的一个位置，与多通道切片将数据分散到多张网卡是同一个模式——多路径并行提升吞吐。
- 布隆过滤器（Bloom Filter） 一种概率性数据结构，用于测试某个元素是否可能存在于集合中，它使用常量内存——类似于计数-最小草图（Count-Min Sketch），但用于成员资格检测而非频率统计。

**学系统，学的是模式，不是代码。** 模式是跨领域的，代码是领域特定的。掌握了模式，你就能在任何系统中识别它、应用它。

### 小结

> 高性能分布式系统不仅使用快速的硬件，还使用智能算法从硬件中提取最大吞吐量。

| 技巧 | 比喻 | 解决的瓶颈 | 核心思想 |
|------|------|-----------|---------|
| 多通道切片 | 高速公路加车道 | 单网卡带宽饱和 | 切片 + 多路径并行 |
| SIEVE 端点池化 | 收费站循环使用 | 连接建立开销 | 池化复用 + 智能淘汰 |
| 拓扑感知路由 | GPS 选最快车道 | 跨 NUMA 惩罚 | 数据本地性 + 自动发现 |
| Count-Min Sketch | 抽样代替普查 | 精确追踪内存爆炸 | 概率近似 + 固定空间 |

四个技巧，四个瓶颈，四个通用模式。它们让数据高速公路不仅快，而且"会思考"——自动选择车道、复用收费站、走最近路线、用抽样做决策。这就是软件智能从硬件中榨取最大吞吐量的方式。
