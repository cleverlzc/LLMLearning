# 写在理解 Mooncake 专家并行之前，详解 MoE 与专家并行EP：为什么"256 个专家只请 8 个"是当前大模型的最优解

> **类型**: 技术原理详解篇
>
> 一家大型工厂有 256 台专用机床（Expert），每台固定在地面上搬不走，但每个产品（Token）只需要 8 台机床加工。MoE 的核心智慧就在这里：工厂可以很大（参数多），但每个产品只激活一小部分机床（计算省）。代价是——这 8 台机床可能分布在不同车间甚至不同厂房，产品必须自己跑过去加工（Dispatch），加工完还要跑回原产线装配（Combine），一来一回跑两趟。路上跑的时间可能比加工时间还长。专家并行（Expert Parallelism）就是那套"物流调度系统"。

MoE（Mixture of Experts，混合专家模型）和专家并行（Expert Parallelism）是LLM大语言模型走向超大规模（如万亿参数）的关键技术组合。

简单来说：MoE 是一种模型架构设计，旨在“用更少的计算量获得更大的模型容量”；而专家并行是一种分布式训练/推理策略，旨在“让巨大的模型能跑得动”。

---

### 引言

2024 年底，DeepSeek-V3 以 6710 亿参数横空出世，但每个 Token 只激活 370 亿——激活率仅 5.5%。2025 年，Kimi K2 更是把专家数推到 384 个。MoE（Mixture of Experts，混合专家）已经成为当前大模型的主流架构。

MoE 的核心矛盾：**模型要大（容量），计算要省（成本）**。稀疏激活解决了这个矛盾，但引入了新问题——专家分布在多个 GPU 上，Token 需要在 GPU 之间来回搬运。这就是专家并行要解决的核心问题。

今天这篇文章，我们从原理出发，把 MoE 和专家并行讲透。

---

### 什么是 MoE（混合专家模型）？

##### 核心思想：专才专用

传统的 Dense（稠密）模型，每一层的所有参数在处理每一个 token 时都会被激活。这就像不管什么问题，都让一个全能博士从头到尾思考一遍，效率低且昂贵。

MoE 的核心思想是：“术业有专攻”。

模型不再由单一的大神经网络组成，而是由许多小的、独立的子网络组成，这些子网络被称为 Experts（专家）。
对于每一个输入的 token，**门控机制（Gating Mechanism）**会根据内容判断它最适合哪个（或哪几个）专家处理。
稀疏激活（Sparse Activation）：只有被选中的少数专家会被激活参与计算，其他专家处于休眠状态。

##### 直观比喻
想象一座大型工厂（模型）：

- Dense 模型：工厂只有一台巨型万能机床，所有产品都必须过这台机器加工。不管生产什么产品，这台机器的全部 1000 个刀头同时运转——生产一颗螺丝钉也要 1000 个刀头全开，浪费严重。
- MoE 模型：工厂有 1000 台专用机床，分为车床组、铣床组、磨床组等。调度员（Router）根据产品类型，只启动对应的几台机床。其他机床待机不耗电。

结果：虽然工厂总设备数（总参数量）很大（比如 1 万台），但每次生产一个产品，只有几台机床在运转（激活参数量小）。

但有一个代价：这 8 台机床固定在不同的车间里，产品必须自己跑到机床那里加工，加工完还要跑回来——**机床搬不走，只能产品自己跑**。跑两趟（送过去 + 收回来）的物流时间，可能比机床加工时间还长。这就是专家并行要解决的核心问题。

### MoE 原理：稀疏激活的数学与直觉

#### MoE 的数学/结构形式
在 Transformer 架构中，将标准的 Feed-Forward Network (FFN) 替换为 MoE Layer：
$$ \text{Output} = \sum_{i \in \text{Top-K}} G(x)_i \cdot E_i(x) $$
*   $x$：输入向量。
*   $G(x)$：门控网络（Gating Network），输出每个专家的权重（通常只保留 Top-K 个最大权重）。
*   $E_i(x)$：第 $i$ 个专家网络。
*   **Top-K**：当前主流 MoE 模型通常 K=8（如 DeepSeek-V3、Kimi K2、Qwen3），早期模型用 K=1 或 K=2（如 Switch Transformer、Mixtral）。

##### 一个 MoE 层长什么样？

在稠密 Transformer 中，每个 Token 经过同一个 FFN（前馈网络）。MoE 把这个 FFN 替换为一组"专家"FFN 和一个"门控网络"（路由器）：

```
稠密 Transformer 层:
  Token → Attention → FFN → 输出
                          ↑ 所有 Token 走同一个 FFN

MoE Transformer 层:
  Token → Attention → Router → Expert 0  ─┐
                               → Expert 3  ─┤ → 加权求和 → 输出
                               → Expert 7  ─┘
                          ↑ 只有被选中的专家参与计算
```

##### 门控路由的数学

MoE 层的输出公式：

```
y = Σ g_i(x) × E_i(x)    (i = 1..N)
```

- `N` = 专家总数（如 256）
- `E_i(x)` = 专家 i 对输入 x 的输出
- `g_i(x)` = 门控权重（大多数为 0，只有 Top-K 个非零）

Top-K 门控的具体步骤：

```
1. 计算 logits:    h(x) = x · W_g        (W_g 是可训练的路由矩阵)
2. Top-K 选择:     只保留 K 个最大的 logits，其余设为 -∞
3. Softmax 归一化: g(x) = softmax(TopK(h(x), K))
4. 稀疏门控:       g_i(x) = softmax 分数（被选中）或 0（未选中）
```

以 DeepSeek-V3 为例：N=256 个路由专家 + 1 个共享专家, K=8。每个 Token 从 256 个路由专家中选 8 个，加上始终激活的共享专家，MoE 层内激活 9/257 ≈ 3.5%。全模型维度（含 Attention 等非 MoE 参数）的激活率为 370 亿/6710 亿 ≈ 5.5%。

##### 为什么稀疏激活这么重要？

| 维度 | 稠密模型 | MoE 模型 |
|------|---------|---------|
| 每个 Token 激活参数 | 全部参数 | 仅 K/N 的参数 |
| 扩展路径 | 更多参数 = 更多 FLOPs | 更多专家 = 更多容量，FLOPs 几乎不变 |
| 内存 | 与计算成正比 | 大（存储所有专家），但计算量小 |
| 路由开销 | 无 | 门控网络计算 + 专家分发 |

关键洞察：**MoE 把"模型容量"和"计算成本"解耦了**。你可以把模型做到万亿参数（容量大），但每个 Token 只花几百亿参数的计算量（成本低）。这就是 DeepSeek-V3 用 6710 亿参数、但推理成本接近 370 亿稠密模型的原因。

##### 共享专家：DeepSeek 的创新

DeepSeek-V3 在 256 个路由专家之外，还加了 1 个共享专家（Shared Expert）。共享专家对每个 Token 都激活，处理通用知识；路由专家处理领域特化知识：

```
Token → Router → 8 个路由专家 (特化知识) ──┐
      → 共享专家 (通用知识) ────────────────┤→ 加权求和 → 输出
                                            │
      不需要路由，永远激活                     │
```

> 笔者注：共享专家的设计动机是——如果某些通用知识（如语法、常识）被所有 Token 需要，让每个路由专家都学一份是浪费。共享专家把这些"公共课"集中到一个专家里，路由专家只学"专业课"，参数效率更高。

### 代表性 MoE 模型一览

| 模型 | 总参数 | 激活参数 | 专家数 | 激活专家 K | 路由方式 | 特色 |
|------|--------|---------|--------|-----------|---------|------|
| **DeepSeek-V3** | 6710 亿 | 370 亿 | 256+1共享 | 8 | Top-8，限4节点 | 无辅助损失负载均衡，MLA，FP8 训练 |
| **Kimi K2** | 1 万亿 | 320 亿 | 384 | 8 | Top-8 | 128 卡 H200 部署，Wide EP |
| **Qwen3-235B** | 2350 亿 | 220 亿 | 128 | 8 | Top-8 | 细粒度专家，共享专家 |
| **Mixtral 8x7B** | 467 亿 | 129 亿 | 8 | 2 | Top-2 | 首个广受关注的开源 MoE |
| **Switch Transformer** | 1.6 万亿 | 可变 | 最多 2048 | 1 | Top-1 | 简化路由，4x 预训练加速 |

> 笔者注：注意趋势——专家数越来越多（8 → 128 → 256 → 384），每个专家越来越小（细粒度专家）。细粒度的好处是路由更灵活：从 256 个小专家中选 8 个，比从 8 个大专家中选 2 个，组合空间大得多（C(256,8) vs C(8,2)），模型表达能力更强。

### 什么是专家并行（Expert Parallelism, EP）？
既然 MoE 让模型变得极大（总参数巨大），单个 GPU 甚至单个节点都存不下所有的”专家”权重。因此，我们需要将不同的专家分布到不同的 GPU 上。这就是专家并行。

继续用工厂比喻：256 台机床太多，一个车间（GPU）放不下，只能分到多个车间。每台机床固定在自己的车间里，不可能搬到别的车间去——**机床不动，产品自己跑**。

##### 核心原理：数据与专家的解耦
在传统的张量并行（TP）或流水线并行（PP）中，每个 GPU 都持有模型所有层的完整副本（或者分片后的层）。但在 EP 中：

每个 GPU 只负责一部分专家。
例如：如果有 8 个专家，分布在 4 个 GPU 上，那么每个 GPU 存储 2 个专家的权重。

##### 工作流程（以训练或推理为例）
路由（Routing）：输入 token 经过门控网络，决定它要去哪个专家。假设 Token A 被路由到专家 1 和专家 3。

Dispatch（送去加工）：Token 必须跑到专家所在的 GPU。

- 如果专家 1 和专家 3 恰好在同一个 GPU 上，直接计算——产品在同一个车间，不用跑远路。
- 如果专家 1 在 GPU 0，专家 3 在 GPU 1，则需要进行 All-to-All 通信——产品要跑到另一个车间去加工。

> 注意：这是 MoE 带来的主要通信开销，也是优化的重点。专家并行需要频繁的跨 GPU/跨节点通信。如果网络带宽不足，GPU 大部分时间在等待数据，计算单元空闲。
解决方案：使用高性能互联（如 NVLink, InfiniBand），优化路由算法（如 GroupSharded MoE）。实现复杂度：传统的 PyTorch/TensorFlow 分布式框架需要修改，当前新的推理框架 vLLM/SGLang/TensorRT-LLM 已适配，处理复杂的数据分片和通信原语。

计算（Computation）：
每个 GPU 使用本地存储的专家权重，对分配给自己的 token 子集进行前向传播计算——机床加工产品。

Combine（收回来装配）：加工完后，结果通过 All-to-All 通信返回给初始的 GPU，加权求和得到最终输出——产品跑回原产线装配。**一来一回，两次 All-to-All，路上跑的时间可能比机床加工时间还长。**

### 专家并行（EP）：当专家住进了不同的 GPU

MoE 的专家数量动辄上百，一张 GPU 放不下所有专家。自然想法：**每个 GPU 放一部分专家**——这就是专家并行（Expert Parallelism, EP）。

##### EP 的基本切分

```
EP=4, 8个专家:
  GPU 0: Expert 0, 1
  GPU 1: Expert 2, 3
  GPU 2: Expert 4, 5
  GPU 3: Expert 6, 7

EP=8, 256个专家 (DeepSeek-V3):
  GPU 0: Expert 0-31   (32个)
  GPU 1: Expert 32-63  (32个)
  ...
  GPU 7: Expert 224-255 (32个)
```

非专家层（Attention、Embedding）不被 EP 切分，通常用 TP（张量并行）或 DP（数据并行）处理。

##### Dispatch/Combine：EP 的核心通信模式

每个 MoE 层涉及两次 All-to-All 通信：

```
┌──────────────────────────────────────────────────────────────────┐
│                      MoE 层的前向传播                              │
│                                                                  │
│  GPU 0        GPU 1        GPU 2        GPU 3                   │
│  [E0,E1]      [E2,E3]      [E4,E5]      [E6,E7]               │
│                                                                  │
│  ① Dispatch (All-to-All): Token 按路由表发到专家所在 GPU          │
│  ──────────────────────────────────────────────────────────      │
│  Token A ──→ E0(GPU0)                                          │
│  Token B ──→ E3(GPU1)                                          │
│  Token C ──→ E5(GPU2)                                          │
│  Token D ──→ E0(GPU0) + E7(GPU3)  ← 一个 Token 可能去多个 GPU   │
│                                                                  │
│  ② Expert Compute: 每个 GPU 对收到的 Token 执行本地专家计算        │
│  ──────────────────────────────────────────────────────────      │
│  GPU 0: E0(Token A, Token D)                                    │
│  GPU 1: E3(Token B)                                             │
│  GPU 2: E5(Token C)                                             │
│  GPU 3: E7(Token D)                                             │
│                                                                  │
│  ③ Combine (All-to-All): 专家输出按权重合并回 Token 原始 GPU      │
│  ──────────────────────────────────────────────────────────      │
│  Token D 的输出 = g_0 × E0(Token D) + g_7 × E7(Token D)        │
│  (从 GPU 0 和 GPU 3 收回，加权求和)                               │
└──────────────────────────────────────────────────────────────────┘
```

| 阶段 | 操作 | 通信模式 | 数据流向 |
|------|------|---------|---------|
| Dispatch | Token 按路由表发送到专家所在 Rank | All-to-All | Token → Expert |
| Expert Compute | 本地专家对收到的 Token 执行前向传播 | 本地计算 | 无通信 |
| Combine | 专家输出按路由权重合并回 Token 所有者 | All-to-All | Expert → Token |

> 笔者注：每个 MoE 层需要 **两次 All-to-All**，这是 EP 最昂贵的开销。All-to-All 是 O(P²) 通信模式（P 个 GPU 两两通信），跨节点时延迟尤其严重——InfiniBand RDMA 带宽约 50 GB/s，远低于节点内 NVLink 的 160 GB/s。

##### EP vs TP vs PP：四种并行方式对比

| 维度 | 数据并行 (DP) | 张量并行 (TP) | 流水线并行 (PP) | 专家并行 (EP) |
|------|-------------|-------------|-------------|-------------|
| 切分什么 | 数据（批次） | 单个算子/张量 | 层（阶段） | 专家 |
| 通信模式 | AllReduce（梯度同步） | AllReduce（每层） | 点对点（阶段间） | All-to-All（每 MoE 层 2 次） |
| 适用范围 | 所有层 | 注意力层 | 所有层 | 仅 MoE 层 |
| 内存节省 | 无（模型完整复制） | 按比例减少每层权重 | 每设备减少总层数 | 仅减少专家权重 |
| 气泡 | 无 | 无 | 流水线气泡 | 无（但有通信开销） |

实际部署采用混合并行策略：**TP 用于注意力，EP 用于专家，DP 用于扩展吞吐量**。例如 DeepSeek-V3 的生产部署：TP=1, EP=32, DP=若干。

### All-to-All 通信：EP 的阿喀琉斯之踵

EP 的性能瓶颈不在计算，而在通信。量化一下这个开销：

##### 通信量估算

以 DeepSeek-V3 为例（EP=8, hidden=7168, FP16）：

```
每个 Token 的 Dispatch 通信量:
  = hidden_dim × 2 bytes (FP16) × 需要跨 GPU 发送的 Token 比例
  ≈ 7168 × 2 × ~87.5% (每个 Token 选 8 个专家，平均 7 个在其他 GPU 上)
  ≈ 12.5 KB/Token

每个 MoE 层的 All-to-All 通信量 (batch=4096 Tokens):
  = 12.5 KB × 4096 × 2 (dispatch + combine)
  ≈ 100 MB

58 个 MoE 层总计:
  ≈ 100 MB × 58 ≈ 5.8 GB 通信量/次前向传播
```

##### 跨节点 vs 节点内

| 通信路径 | 带宽 | DeepSeek-V3 单层 All-to-All 延迟 |
|---------|------|--------------------------------|
| NVLink（节点内） | ~160 GB/s | ~0.5 ms |
| InfiniBand RDMA（跨节点） | ~50 GB/s | ~1.7 ms |
| TCP（回退） | ~10 GB/s | ~8.7 ms |

> 笔者注：跨节点 All-to-All 延迟是节点内的 3-4 倍。对于 58 层 MoE，跨节点 EP 每次前向传播的通信开销约 100ms，占总推理时间的 30-50%。这就是为什么 DeepSeek-V3 限制每个 Token 最多路由到 4 个节点——减少跨节点通信次数。

##### 负载不均衡：雪上加霜

All-to-All 通信的延迟取决于最慢的那个 GPU。如果某个 GPU 上的专家特别热门，收到的 Token 远多于其他 GPU，它就成了瓶颈：

```
理想情况 (负载均衡):
  GPU 0: 512 Tokens → 处理 0.5ms
  GPU 1: 512 Tokens → 处理 0.5ms
  GPU 2: 512 Tokens → 处理 0.5ms
  GPU 3: 512 Tokens → 处理 0.5ms
  总延迟: 0.5ms (取最慢的)

不均衡情况:
  GPU 0: 200 Tokens → 处理 0.2ms
  GPU 1: 200 Tokens → 处理 0.2ms
  GPU 2: 200 Tokens → 处理 0.2ms
  GPU 3: 1448 Tokens → 处理 1.4ms  ← 热门专家集中在此
  总延迟: 1.4ms (取最慢的) → 吞吐下降 2.8x
```

DeepSeek-V3 的解法：**无辅助损失的负载均衡**——用可学习的逐专家偏差（bias）调整路由 logits，而不是传统的辅助损失函数。偏差在训练中自动调整，让 Token 均匀分配到各专家。

### DeepEP：让 All-to-All 跑满带宽

DeepEP（DeepSeek-AI, 2025.2）是专为 MoE 专家并行设计的通信库，核心贡献是让 All-to-All 通信逼近硬件理论带宽。

##### 两种内核模式

| 模式 | 适用场景 | 通信路径 | 特点 |
|------|---------|---------|------|
| **普通内核** | 训练 / Prefill | NVLink + RDMA | 高吞吐量 |
| **低延迟内核** | Decode（推理） | 纯 RDMA (NVSHMEM) | 低延迟 |

##### 性能数据

| 通信路径 | DeepEP 实测 | 理论峰值 | 利用率 |
|---------|-----------|---------|--------|
| NVLink（节点内） | 153-158 GB/s | 160 GB/s | ~95% |
| InfiniBand RDMA（跨节点） | 43-47 GB/s | 50 GB/s | ~90% |

##### 关键优化技术

**1. 计算-通信重叠**

传统方式：先通信，再计算，串行执行。DeepEP 用双微批量流水线，让通信和计算重叠：

```
传统方式:
  [Dispatch Batch1] [Compute Batch1] [Combine Batch1] [Dispatch Batch2] [Compute Batch2] ...

重叠方式:
  [Dispatch Batch1] [Dispatch Batch2 + Compute Batch1] [Combine Batch1 + Compute Batch2] ...
                     ↑ 通信和计算同时进行
```

**2. 原生 FP8 分发**

Token 在 Dispatch 前量化为 FP8（8 位），通信量减半，Combine 后反量化回 BF16/FP16：

```
输入: BF16 Token (16 bit)
    │
    ▼ FP8 量化
传输: FP8 数据 (8 bit) + FP32 scales → 通信量减半
    │
    ▼ FP8 反量化
专家计算: BF16/FP16
```

**3. 接收钩子（Receive Hook）**

允许在 RDMA 数据到达的同时就开始专家计算，不必等所有数据到齐：

```
传统: 等所有 Token 到齐 → 开始计算
Hook: Token 到一批算一批，边收边算
```

> 笔者注：DeepEP 的低延迟内核专门为 Decode 阶段优化。Decode 的特点是每个 GPU 只有少量 Token（batch size 小），All-to-All 的延迟比吞吐量更重要。低延迟内核用 NVSHMEM 做 RDMA 直传，绕过传统 NCCL 的集合通信路径，延迟可降低 2-3 倍。

### EP 与 PD 解耦的交汇

EP 和 PD 解耦（Prefill-Decode Disaggregation）是两个正交的优化维度，但它们自然互补：

```
                    Prefill 集群                    Decode 集群
                 (计算密集, 大 batch)             (内存密集, 小 batch)
                 ┌─────────────────┐            ┌─────────────────┐
                 │  Attention (TP)  │            │  Attention (TP)  │
                 │  Expert (EP)     │            │  Expert (EP)     │
                 │  DeepEP 普通内核  │            │  DeepEP 低延迟内核 │
                 └─────────────────┘            └─────────────────┘
                         │                              │
                         └──── KV Cache 传输 ────────────┘
                              (Transfer Engine)
```

| 维度 | Prefill | Decode |
|------|---------|--------|
| EP 通信模式 | 大 batch，吞吐优先 | 小 batch，延迟优先 |
| DeepEP 内核 | 普通内核（高吞吐） | 低延迟内核（低延迟） |
| EP 规模 | 中等（EP=8-16） | 大（EP=64-128, Wide EP） |
| 瓶颈 | 计算 | All-to-All 通信延迟 |

##### Wide EP：Decode 的杀手锏

Decode 阶段的 batch size 小，单 GPU 上的 Token 数少，专家计算量不足以为通信"遮掩"。Wide EP 的思路：**用更多 GPU 分摊专家，每个 GPU 的 Token 数更少，但专家更少、计算更快**。

```
普通 EP (EP=8):
  每个 GPU: 32 个专家, 512 Tokens → 计算 5ms, 通信 1.7ms

Wide EP (EP=64):
  每个 GPU: 4 个专家, 64 Tokens → 计算 0.6ms, 通信 1.7ms
  ↑ 计算大幅减少，但通信不变 → 通信占比上升
  ↑ 但总延迟降低 (5+1.7=6.7ms → 0.6+1.7=2.3ms)
```

LMSYS 在 128 张 H200 上部署 Kimi K2（384 专家），使用 Wide EP + PD 解耦，实现了 2.2k tok/s/H200 的吞吐。

##### 注意力-专家分离（Janus, 2025）

更激进的解耦：把 Attention 和 Expert 也分开部署到不同的 GPU 组：

```
传统混合部署:              注意力-专家分离 (Janus):
┌──────────────┐          ┌──────────┐    ┌──────────┐
│ Attention    │          │Attention │    │ Expert   │
│ + Expert     │          │ GPU 池    │    │ GPU 池    │
│ (同一 GPU)   │          │(存 KV    │    │(纯计算,  │
└──────────────┘          │ Cache)   │    │Wide EP)  │
                          └──────────┘    └──────────┘
```

优势：Expert GPU 可以用 Wide EP 而不复制 Attention 权重，Attention GPU 的全部显存用于 KV Cache。

> 笔者注：注意力-专家分离听起来很美，但 2026 年 2 月的论文《Revealing the Challenges of Attention-FFN Disaggregation》指出，实际部署中仍面临重大挑战——主要是分离后的通信开销（Attention→Expert 的额外一跳）和调度复杂度。目前该方向仍在积极探索中。

### FP8 量化：EP 通信的"减半术"

FP8 对 EP 尤其重要，原因有三：

1. **EP 是通信受限的**：All-to-All 是瓶颈，通信量减半直接缓解瓶颈
2. **MoE 专家是独立单元**：每个专家可以独立量化，精度损失比整模型量化更小
3. **DeepSeek-V3 原生 FP8 训练**：模型权重和激活值已是 FP8，通信时无需额外量化开销

实测数据（来自 MoE-Inference-Bench）：

| 场景 | FP16 吞吐 | FP8 吞吐 | 提升 |
|------|----------|---------|------|
| Mixtral-8x7B (大 batch) | 基准 | +25-30% | 通信量减半的效果 |
| MoE vs 稠密模型的 FP8 收益 | +31% | +69-74% | MoE 从 FP8 获益是稠密模型的 2.2x |

> 笔者注：MoE 从 FP8 获益远超稠密模型（+69% vs +31%），根本原因是 MoE 的计算-通信比更偏向通信。FP8 减半通信量，对通信受限的 MoE 是雪中送炭，对计算受限的稠密模型只是锦上添花。

### 设计哲学：MoE 与 EP 的三大矛盾

| 矛盾 | 含义 | 解决方案 |
|------|------|---------|
| **容量 vs 计算** | 模型要大，计算要省 | 稀疏激活——大模型小计算 |
| **通信 vs 延迟** | 专家分布越广，通信越贵 | DeepEP 优化内核 + FP8 减半通信量 + 计算-通信重叠 |
| **均衡 vs 精度** | 强制均衡降低模型质量 | 无辅助损失均衡（可学习 bias）+ Wide EP 降低单 GPU 负载 |

### 总结与行动指南

| 核心概念 | 一句话总结 |
|---------|----------|
| MoE 稀疏激活 | 256 个专家只请 8 个，模型容量与计算成本解耦 |
| Top-K 门控 | Router 打分 → 选 Top-K → Softmax 归一化 → 稀疏加权求和 |
| 共享专家 | 通用知识集中到一个专家，路由专家只学特化知识 |
| 专家并行 (EP) | 每个 GPU 放一部分专家，Token 按路由表跨 GPU 分发 |
| Dispatch/Combine | 每个 MoE 层两次 All-to-All：发出去 + 收回来 |
| DeepEP | 95% NVLink 带宽利用率 + 低延迟内核 + FP8 + 计算通信重叠 |
| Wide EP | 用更多 GPU 分摊专家，降低单 GPU 延迟 |
| FP8 通信 | 通信量减半，MoE 获益是稠密模型的 2.2 倍 |

**建议**: 部署 MoE 模型时，Prefill 用 DeepEP 普通内核（吞吐优先），Decode 用低延迟内核 + Wide EP（延迟优先）——这是当前业界验证过的最优组合。
