# 写在理解 Mooncake 之前，RoCE 演进史：RDMA 如何从"贵族专享"变成"AI 基建标配"

> **系列**: Mooncake 技术博客系列 | **类型**: 前置知识篇
>
> 读 Mooncake 源码时，你会反复碰到一个词——RDMA。Transfer Engine 的零拷贝传输、PD 解耦的 KV Cache 瞬移、EP 的 GPU 直传，底层全靠它。而今天 AI 集群里跑的 RDMA，十有八九是 **RoCE v2**——一种让 RDMA 跑在普通以太网上的协议。RoCE 不是一夜之间冒出来的，它经历了从"贵族专享"到"大众基建"的二十年斗争。

前面通过 LMCache 和 vLLM 两个业界最有名的开源项目拆解，分别写了两个系列的技术博客文章，想必各位读者、一线工程师、想要转行AI Infer Infra的朋友们已经对推理系统和KV Cache已经了解的非常清楚了。

接下来将拆解另一个非常有名的KV Cache系统：Mooncake。企业级解耦式（也叫分离式，与推理系统解耦，独立KV Cache存储）分布式 KVCache 标杆。

写在深入理解Mooncake之前，先来了解RDMA/RoCE的这段历史，才能理解 Mooncake 为什么这样设计网络层。

---

### 引言

想象一座城市，有钱人住在封闭的私家花园社区（InfiniBand），里面修了专用高速路，只有会员能走，又快又贵。普通市民只能走公共马路（TCP/IP），虽然谁都能走，但红绿灯多、堵车严重、速度慢。

RoCE 的故事，就是"如何把私家高速路扩展成公共马路"的故事——既要有高速路的速度，又要让所有人都能用。这个故事走了二十年，经历了五次关键转折，最终在 AI 时代修成正果。

今天这篇文章，我们按时间线走一遍 RoCE 的演进之路，搞清楚每个阶段解决了什么问题、又引入了什么新问题。这是理解 Mooncake 网络层设计的前置知识。

---

### 一、InfiniBand 时代：私家花园里的高速路（2000-2005）

在 RoCE 出现之前，高性能计算（HPC）和早期数据中心只有两条路可走：**要么忍受以太网的慢，要么花钱建设 InfiniBand**。

##### InfiniBand 的优势

| 特性 | InfiniBand | 传统以太网 (TCP/IP) |
|------|-----------|-------------------|
| 延迟 | 1-2 μs | 50-100 μs |
| CPU 占用 | 极低（硬件卸载） | 高（内核协议栈） |
| 拥塞控制 | 硬件内置（LCM） | 软件实现（TCP） |
| 带宽 | 10G→40G→200G | 1G→10G |

InfiniBand 天生为 RDMA 设计：网卡硬件直接读写内存，CPU 完全不参与数据传输。这在 HPC 场景下是刚需——成千上万个计算节点之间频繁交换消息，如果每次传输都要 CPU 中断 + 内核拷贝，计算节点早就被网络拖垮了。

##### InfiniBand 的致命问题

| 问题 | 说明 |
|------|------|
| **昂贵** | 专用交换机、网卡、线缆，成本是以太网的 3-5 倍 |
| **封闭** | 生态不开放，只有 Mellanox（现 NVIDIA）、Cisco 等少数厂商支持 |
| **隔离** | IB 网络与以太网/IP 网络完全隔离，需要两套运维体系 |
| **不可路由** | IB 使用 LID 寻址，无法跨越三层网络 |

> 笔者注：InfiniBand 的"封闭"不仅仅是技术问题，更是商业问题。Mellanox 几乎垄断了 IB 生态，从网卡到交换机到协议栈，全是私有方案。这让大型互联网公司非常不舒服——他们不想被单一供应商绑架。

**此时没有 RoCE**。大家要么花大价钱买 IB，要么忍受以太网的高延迟。两条路都不理想。

---

### 二、RoCE v1：第一次"搬家"尝试（2005-2009）

为了让 RDMA 跑在以太网上，业界做了第一次尝试：**把 IB 的链路层帧直接塞进以太网帧里**。

##### 技术方案

```
┌──────────────────────────────────────────────┐
│              RoCE v1 报文封装                 │
│                                              │
│  ┌──────────┬──────────────────────────┐     │
│  │ 以太网头  │     IB 传输层报文          │     │
│  │(EtherType│  (GRH + IB Payload)      │     │
│  │ =0x8915) │                          │     │
│  └──────────┴──────────────────────────┘     │
│                                              │
│  关键：没有 IP 头！没有 UDP 头！                 │
│  就像把一封 IB 信直接塞进以太网信封               │
└──────────────────────────────────────────────┘
```

##### 致命缺陷：不可路由

| 特性 | RoCE v1 | 说明 |
|------|---------|------|
| 封装 | 以太网帧 | EtherType 0x8915 |
| 网络层 | 无 | 没有 IP 头部 |
| 路由能力 | **不可路由** | 只能在同一个 VLAN 内通信 |
| 跨子网 | 不支持 | 无法跨越路由器 |

RoCE v1 就像在一个城市内部修了一条高速路，但这条高速路不通向其他城市。你可以用 IB 的速度在同 VLAN 内通信，但无法利用现有的 IP 网络基础设施——路由器、防火墙、负载均衡器全都不认这个包。

> 笔者注：RoCE v1 本质上只是"换了物理层介质的 InfiniBand"。它解决了"用便宜网线"的问题，但没解决"网络孤岛"的问题。企业部署后发现，还是得维护一套与 IP 网络完全隔离的二层网络，运维成本没有真正降低。

**结果**：RoCE v1 市场反响平平，更多被视为 IB 的一种"廉价替代方案"，并未成为主流。

---

### 三、RoCE v2：真正的革命——拥抱 IP 网络（2009-2013）

这是 RoCE 历史上的**转折点**。业界意识到：如果想让 RDMA 普及，必须让它成为 IP 网络的一部分，而不是旁观者。

##### 技术突破：UDP/IP 封装

```
┌──────────────────────────────────────────────────────┐
│                 RoCE v2 报文封装                      │
│                                                      │
│  ┌──────────┬──────────┬──────────┬──────────────┐   │
│  │ 以太网头  │  IP 头   │ UDP 头   │  IB 传输层     │   │
│  │          │ (可路由)  │(端口4791)│  报文         │   │
│  └──────────┴──────────┴──────────┴──────────────┘   │
│                                                      │
│  关键变化：加了 IP 头 + UDP 头                          │
│  RDMA 报文现在可以像普通 TCP 流量一样穿越路由器            │
└──────────────────────────────────────────────────────┘
```

##### v1 vs v2 关键对比

| 特性 | RoCE v1 | RoCE v2 |
|------|---------|---------|
| 封装 | 以太网帧 | **UDP/IP** |
| 网络层 | 无 | **IPv4/IPv6** |
| 路由能力 | 仅二层 | **三层可路由** |
| 跨子网 | 不支持 | **支持** |
| UDP 端口 | - | **4791** |
| 现有基础设施 | 不可利用 | **可复用路由器、防火墙等** |
| 市场地位 | 已淘汰 | **当前主流标准** |

RoCE v2 的意义怎么强调都不过分：**它让 RDMA 从"专用网络协议"变成了"IP 网络公民"**。企业不再需要维护两套网络，RDMA 流量可以和普通 TCP 流量跑在同一套 IP 基础设施上。

> 笔者注：当你现在谈论"RoCE"时，默认指的都是 RoCE v2。RoCE v1 已经基本退出历史舞台。Mooncake 的 RDMA 传输层也是基于 RoCE v2 实现的。

---

### 四、无损以太网：RoCE 的"基础设施补课"（2013-2016）

RoCE v2 解决了"连通性"问题，但引发了新的灾难：**以太网不认识 RDMA，不会给它让路**。

##### 问题：UDP 没有拥塞控制

```
InfiniBand 网络：
  拥塞 → 交换机硬件自动降速 → 不丢包 → 性能稳定

RoCE v2 网络：
  拥塞 → UDP 不管 → 交换机缓冲区溢出 → 丢包 → RDMA 性能断崖式下跌
                                         ↑
                              RDMA 对丢包极其敏感！
                              一个丢包可能导致整个传输超时重传
```

TCP 丢包了会自动降速重传，虽然慢但能恢复。RDMA 丢包了？性能直接从 100GB/s 掉到 10GB/s，甚至更低。因为 RDMA 的传输语义假设底层是**可靠的无损网络**——这是 InfiniBand 天然提供的，但以太网天然不提供。以太网的逻辑是“尽力而为”。

##### 三件套解决方案

业界花了三年时间，给以太网"补课"，形成了 RoCE 运行的**必要条件**：

| 组件 | 全称 | 作用 | 类比 |
|------|------|------|------|
| **PFC** | Priority Flow Control (IEEE 802.1Qbb) | 缓冲区快满时，通知上游暂停发送 | 高速公路入口匝道灯控 |
| **ECN** | Explicit Congestion Notification (RFC 3168) | 交换机标记拥塞信号，通知发送方降速 | 路边电子屏提示"前方拥堵，减速" |
| **DCQCN** | Data Center Quantized Congestion Notification | 结合 PFC + ECN，形成完整的速率调节闭环 | 匝道灯 + 电子屏 + 自动巡航协同工作 |

##### DCQCN 工作流

```
                    ① 拥塞检测
        ┌──────────────────────────────┐
        │  交换机：队列深度 > 阈值        │
        │  → 标记 IP 头 ECN 位 (01)     │
        └──────────────┬───────────────┘
                       │
                       ▼
                    ② 拥塞通知
        ┌──────────────────────────────┐
        │  接收方：检测到 ECN 标记        │
        │  → 发送 CNP (Congestion       │
        │    Notification Packet) 给源  │
        └──────────────┬───────────────┘
                       │
                       ▼
                    ③ 速率调节
        ┌──────────────────────────────┐
        │  发送方：收到 CNP              │
        │  → 降低发送速率（指数衰减）      │
        │  → 网络恢复后逐渐加速（线性恢复） │
        └──────────────────────────────┘
```

> 笔者注：PFC 是一把双刃剑。它防止了丢包，但引入了**队头阻塞（HoL Blocking）**——一个流的拥塞会导致同优先级的所有流都被暂停。如果 PFC 配置不当，甚至可能引发**PFC 风暴**，整个网络瘫痪。这也是为什么 RoCE 网络的交换机配置非常讲究——不是插上网线就能跑的。

**这一阶段确立了铁律**：没有 PFC + ECN + DCQCN，RoCE 在以太网上无法稳定运行。这也意味着数据中心交换机必须升级为支持无损特性的高端交换机。

### 五、AI 爆发：RoCE 的第二春（2017-至今）

深度学习和大模型训练的爆发，让 RoCE 从"小众高性能技术"变成了"AI 基建标配"。

##### 驱动因素

| 驱动力 | 说明 |
|--------|------|
| GPU 集群规模爆炸 | 从几十张卡扩展到数万张卡（A100/H100 集群） |
| 通信成为瓶颈 | GPU 计算速度远超网络通信速度，TCP 成为训练瓶颈 |
| NVIDIA 收购 Mellanox | ConnectX 网卡 + BlueField DPU + NCCL 深度绑定 RoCE |
| AI 框架原生支持 | PyTorch/TensorFlow 通过 NCCL 无缝接入 RoCE 网络 |

##### RoCE vs InfiniBand：当前格局

| 维度 | InfiniBand (NDR) | RoCE v2 (400G) |
|------|-----------------|----------------|
| 延迟 | 0.6-1 μs | 1-2 μs |
| 带宽 | 400 Gbps | 400 Gbps |
| 拥塞控制 | 硬件内置，自适应 | 需要配置 PFC/ECN/DCQCN |
| 成本 | 高（专用交换机） | 低（通用以太网交换机） |
| 运维 | 简单（自管理） | 复杂（需调优无损网络） |
| 生态 | NVIDIA 为主 | 开放，多厂商 |
| 市场份额 | 高端 HPC | **AI 集群主流** |

> 笔者注：在 Mooncake 的生产部署中，Kimi 的推理集群使用的是 RoCE v2 网络（4×200 Gbps ConnectX-6/7 网卡）。选择 RoCE 而非 InfiniBand 的核心原因不是性能——两者在 200Gbps 级别差距不大——而是**成本和灵活性**：以太网交换机更便宜，且可以复用现有的 IP 网络运维体系。

### 六、RoCE 在 LLM 推理中的角色：为什么 Mooncake 离不开它

理解了 RoCE 的演进，再看 Mooncake 的网络层设计就一目了然了。

##### LLM 推理的网络需求

| 场景 | 数据量 | 延迟要求 | 协议选择 |
|------|--------|---------|---------|
| PD 解耦：KV Cache 传输 | 10-100 GB/请求 | < 1s | **RDMA (RoCE v2)** |
| EP：MoE Token dispatch/combine | 1-10 GB/step | < 100 μs | **RDMA (RoCE v2)** |
| P2P Store：模型权重分发 | 100 GB-1 TB | < 30s | **RDMA (RoCE v2)** |
| 元数据同步 | KB 级 | 秒级 | TCP (etcd/gRPC) |

KV Cache 传输是 Mooncake 最核心的网络操作。一个 70B 模型的 Prefill 阶段产生的 KV Cache 可达 40-100 GB，如果用 TCP 传输需要数秒，CPU 占用极高；用 RDMA 传输只需亚秒级，CPU 几乎不参与。

##### Mooncake 对 RoCE 的深度利用

```
┌─────────────────────────────────────────────────────────┐
│                    Mooncake 网络层                       │
│                                                         │
│  ┌─────────────────────────────────────────────────┐    │
│  │              Transfer Engine                    │    │
│  │  ┌────────────┐  ┌──────────┐  ┌────────────┐   │    │
│  │  │ RDMA Transport │ │ NVLink   │  │ TCP      │  │    │
│  │  │ (RoCE v2)   │  │ Transport│  │ Transport  │  │    │
│  │  └──────┬─────┘  └──────────┘  └────────────┘   │    │
│  └─────────┼───────────────────────────────────────┘    │
│            │                                            │
│  ┌─────────▼───────────────────────────────────────┐    │
│  │  RoCE v2 能力利用                                │    │
│  │  • 多网卡带宽聚合（4×200G → 87 GB/s）              │    │
│  │  • GPUDirect RDMA（GPU 显存直传，无需 CPU 中转）    │    │
│  │  • 拓扑感知路由（NUMA 亲和 + 网卡选择）              │    │
│  │  • QP 连接管理（SIEVE 淘汰 + 批量传输）             │    │
│  └─────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────┘
```

### 七、未来展望：RoCE 的下一步

| 方向 | 说明 | 对 Mooncake 的意义 |
|------|------|-------------------|
| **NVLink/NVSwitch 补充** | 机柜内用 NVLink（GPU 直连），RoCE 承担跨机柜通信 | Mooncake 已支持 NVLink Transport 做节点内传输 |
| **SmartNIC/DPU 卸载** | 拥塞控制、协议处理从 CPU 转移到网卡/DPU | 降低主机 CPU 负担，简化无损网络配置 |
| **更高带宽** | ConnectX-8 支持 800G，下一代 1.6T | 更大模型、更长上下文的 KV Cache 传输 |
| **Ultra Ethernet Consortium** | NVIDIA/AMD/Intel 等联合推进超以太网标准 | 可能带来原生无损以太网，不再需要 PFC 补课 |

### 演进时间线总结

```
2000        2007        2012        2014        2017        2024
  │           │           │           │           │           │
  ▼           ▼           ▼           ▼           ▼           ▼
 IB统治    RoCE v1     RoCE v2     PFC/ECN/     AI爆发     400G RoCE
 专用网络   不可路由     UDP/IP      DCQCN       NCCL普及    AI集群标配
 昂贵封闭   市场平平     可路由！     无损以太网   GPU集群     Mooncake
            ↓           ↓           ↓           ↓           ↓
          "兼容尝试"  "真正革命"  "基础设施补课"  "第二春"   "基建标配"
```

| 阶段 | 核心突破 | 遗留问题 |
|------|---------|---------|
| InfiniBand (2000s) | 原生 RDMA，极低延迟 | 昂贵、封闭、不可路由 |
| RoCE v1 (2007) | 跑在以太网物理层上 | 不可路由，仍是网络孤岛 |

| DCQCN (2014) | PFC + ECN 实现无损以太网 | 配置复杂，交换机要求高 |
| AI Era (2017+) | NCCL + GPU 集群驱动普及 | 网络调优难度极大 |

### 结语：理解 RoCE，才能理解 Mooncake

RoCE 的演进史告诉我们一个道理：**高性能不是天上掉下来的，是一层一层"补课"补出来的**。从 IB 的原生无损，到 RoCE v1 的勉强兼容，到 RoCE v2 的 IP 融合，再到 DCQCN 的无损补课——每一层都在解决上一层引入的问题。

Mooncake 的网络层设计，正是建立在这些"补课"成果之上的。Transfer Engine 的 RDMA Transport 默认走 RoCE v2，依赖 PFC/ECN 保证无损传输；GPUDirect RDMA 依赖 dmabuf 机制绕过 CPU；多网卡带宽聚合依赖 RoCE v2 的路由能力做拓扑感知。

**建议**：如果你在部署 Mooncake，先把 RoCE v2 的无损网络配好（PFC + ECN + DCQCN）——这是所有性能优化的前提，网络基础没打好，上层怎么调都是白费。
